## Kuma bootstrap is guarded, not silently provisioned

Kuma 2.5.12 exposes a first-run setup wizard; its documented initial-admin environment variables were added only in v3. They are not fabricated here, and no unsupported setup CLI or direct admin database insertion is used. `KUMA_UI_PASSWORD_HASH` must be a real privately managed bcrypt hash with cost 12–16; missing/invalid values stop startup before any listener. Generate it privately with the pinned Caddy `hash-password` interactive command, store only the hash in Render secret env, and privately retain the distinct operator Basic password. There is no shipped credential.

Kuma's native server binds **127.0.0.1:3001**, and its read-only readiness helper binds **127.0.0.1:3002**. Only Caddy binds the Render public HTTP `$PORT`. Every UI/setup/socket route is behind mandatory `operator` Basic auth; the direct `onrender.com` hostname cannot bypass this guard. Caddy authenticates WebSocket upgrades and strips Basic/Proxy authorization before forwarding. Render edge TLS is required for all external use; never use public HTTP for credentials. Caddy automatic HTTPS and admin API are off, config persistence is off, and its diagnostics are discarded to avoid request metadata logging. There is no ACME disk.

Initial `KUMA_BOOTSTRAP_WINDOW_APPROVED=false` and `KUMA_BOOTSTRAP_COMPLETE=false` block startup. The main operator must approve a narrow bootstrap window, set the real hash privately, and temporarily set `KUMA_BOOTSTRAP_WINDOW_APPROVED=true`. A plan-supported Render IP allowlist may additionally restrict this window, but no paid workspace upgrade or unsupported IP rule is assumed. The setup wizard then remains reachable only after operator Basic authentication. Create the native Kuma admin through that guarded wizard using a separate strong password, leave native authentication enabled, enable native MFA where supported, and do not create a public status page or test notification.

`/livez` confirms only the local process and is initial Render health so guarded setup can remain alive. **`/healthz` stays 503** until `KUMA_BOOTSTRAP_COMPLETE=true`, read-only SQLite finds an active native admin, and native `disableAuth` is not enabled. Final affected container checks passed SQLite binding, native guarded setup/admin/login, persisted restart login and false-completion **503** versus true-completion/restart **200**; mocks separately cover missing/corrupt state/disabled auth. Actual Render disk/readiness still require acceptance without hidden user overrides. After supported setup, set bootstrap window false and verify `/healthz`; changing the new service's Render check to `/healthz` is separately reviewed. A boolean does not fabricate an admin.

## ntfy authentication and mobile consent

The real HTTPS base URL is derived at boot as `NTFY_BASE_URL=https://$RENDER_EXTERNAL_HOSTNAME`; only the exact named Render host family is accepted. The public socket is plain HTTP `:$PORT`, behind Render edge TLS. Auth and cache persist in `/var/lib/ntfy/auth.db` and `/var/lib/ntfy/cache.db`; anonymous default and explicit wildcard ACL are deny-all. Signup, web UI, attachments, SMTP, Firebase and web push are disabled.

Initial startup requires separate `NTFY_BOOTSTRAP_APPROVED=true` and privately supplied `NTFY_ADMIN_PASSWORD_HASH`. The entrypoint initializes the native auth DB on **loopback only** first, stops that process, then uses verified native `ntfy user ... add --role=admin operator` with `NTFY_PASSWORD_HASH` and `ntfy access ... everyone '*' deny`. CLI output is discarded; no secrets are placed in argv or printed. A persistent marker prevents ordinary reboot password changes. Existing users without a marker cause provisioning to fail rather than being silently trusted. Restoring/moving an auth DB requires explicit operator review of the marker and credentials.

The server starts with a cleared environment and the fixed config so inherited `NTFY_*` cannot enable relay or signup. `NTFY_UPSTREAM_ENABLED` must remain `false`; `upstream-base-url` and upstream token remain empty. **iPhone/APNs relay metadata consent is not approved.** No instant iPhone paging claim is made. ## Alertmanager and alert ingress

Alertmanager listens on private `0.0.0.0:9093`, clustering is disabled, and silences/notification log state persists in `/alertmanager`. Its pinned image runs as `nobody`; the entrypoint fails if that exact mounted disk is not writable. The operator must verify Render disk ownership without broad public permissions before release. Its UI/admin API remains private to the workspace/network; no custom domain or public service is defined for it.

The shipped Alertmanager receiver is `notifications-disabled` with no webhook. This is a safe OFF configuration, **not a production queue**: never enable producers/outbox against it, because Alertmanager could accept an event without delivery. PostgreSQL outbox gates stay OFF and no migration is run. Alertmanager state is not a replacement for the durable application outbox.

The separate public gateway offers a static GET/HEAD `/healthz`, and only POST `/api/v2/alerts` behind `publisher` Basic auth. A real `ALERT_PUBLISHER_PASSWORD_HASH` is required. `ALERTMANAGER_PRIVATE_HOST` is injected from the approved private service via `fromService.property: host`; entrypoint validation rejects URL credentials, alternate hosts, path/query, ports or whitespace and fails closed. No request-derived upstream or public proxy fallback exists.

The body cap is exactly **2048 bytes**, including fixed Content-Length enforcement. Requests without Content-Length, including chunked framing, are rejected with 411 before upstream contact; framed oversize requests receive 413. Caddy strips Authorization/Proxy-Authorization/Cookie, fixes the upstream path, explicitly clears query strings, and does not expose GET alerts, UI, silences or reload. Offline tests assert these denies, exactly-2KB acceptance, no oversized/chunked upstream call, and no upstream publisher credential. Health reports only gateway liveness, not end-to-end delivery.

## Backup, restore, rollback

Before activation, define an operator-owned backup/restore procedure outside this public repository. Never rely on a redeploy to reconstruct disk state. Review Render disk snapshot support and retention in the correct dashboard rather than assuming coverage. Stop writers for consistent filesystem backups, or use the product-supported SQLite online backup method; raw copying a running `.db` without its WAL is unsafe. Kuma `/app/data` includes admin/monitor state and uploads; ntfy `/var/lib/ntfy` includes auth/cache and the provision marker; Alertmanager `/alertmanager` includes silences and notification state. Treat all as sensitive, encrypt/access-restrict backups and retain privately, never in Git. The existing PostgreSQL outbox requires its own approved managed DB backup/restore process and no new DB definition.

Restore to the same reviewed software version first, leave producers/worker/notifications OFF, and verify disk permissions, admin auth, ntfy deny-all ACL/token roles, closed Kuma readiness and private Alertmanager access before enabling anything. Keep gateway hash and subscriber/publisher credentials distinct; rotate compromised credentials rather than copying them into logs. Audit queue/destination fingerprints and pending records with the incident owner before activation; do not discard pending deliveries, rebind destinations or backfill production alerts. Rolling back a software digest does not reverse a database schema change. Any migration/restore needing existing production DB changes is a separate approval gate.
